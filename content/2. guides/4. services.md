## What are services?

In Charcole, **services are where your application thinks**.

If controllers are responsible for handling HTTP requests, and repositories are responsible for handling data, then services sit right in the middle and decide **what should actually happen**.

Services contain your **business logic**.  
They represent the rules, decisions, and workflows that define how your application behaves.

They do not care about Express.  
They do not care about HTTP status codes.  
They do not care about where the data comes from.

They only care about **what needs to be done**.

---

## Why services exist

In many backend projects, business logic slowly leaks into controllers. At first it feels harmless — a small condition here, a small query there. Over time, controllers become bloated, unreadable, and impossible to test.

Charcole deliberately separates services to prevent this.

By forcing all business logic into services, Charcole ensures that controllers stay thin, repositories stay focused, and your application remains understandable as it grows.

Services are not an extra layer for complexity.  
They are a **boundary that protects your codebase**.

---

## What belongs in a service

A service answers questions like:

- Can this action be performed?
- What happens next?
- Which data do we need?
- Which repositories should be involved?
- What rules must be enforced?

Services often:
- Combine data from multiple repositories
- Apply validation and business rules
- Decide whether an operation should succeed or fail
- Orchestrate complex workflows

This is the layer where your application’s **intent** lives.

---

## What does NOT belong in a service

Services should remain independent from transport and storage concerns.

They should not:
- Read from `req` or write to `res`
- Return HTTP responses
- Handle Express-specific objects
- Perform raw database queries directly

Those responsibilities belong to controllers and repositories respectively.

This separation keeps services reusable, testable, and stable.

---

## Services in the Charcole flow

Charcole follows a very intentional flow:

Request → Controller → Service → Repository → Database


The controller receives the request and delegates the work.  
The service decides what needs to happen.  
The repository fetches or persists data.

Each layer has a single responsibility, and dependencies only flow in one direction.

This is not accidental. This is what keeps systems sane.

## Example service

### JavaScript

```js
// src/modules/user/user.service.js
import { UserRepository } from '../../repositories/user.repository.js'

export async function createUser(payload) {
  const existingUser = await UserRepository.findByEmail(payload.email)

  if (existingUser) {
    throw new Error('User already exists')
  }

  return UserRepository.create(payload)
}
```
### TypeScript

```ts
// src/modules/user/user.service.ts
import { UserRepository } from '../../repositories/user.repository'

export async function createUser(payload: CreateUserDTO) {
  const existingUser = await UserRepository.findByEmail(payload.email)

  if (existingUser) {
    throw new Error('User already exists')
  }

  return UserRepository.create(payload)
}
```

Notice how the service:
- Does not know about HTTP
- Does not know about routes
- Does not care how data is stored

It only enforces **business rules**.

## Why services make your backend powerful

Services are where complexity belongs.

As your application grows, logic becomes richer. Conditions multiply. Workflows become layered. Without services, this complexity spreads everywhere and becomes unmanageable.

With services, complexity is contained, intentional, and readable.

They also make testing straightforward. Services can be tested in isolation by mocking repositories, without spinning up servers or databases.

This is where backend development stops feeling fragile and starts feeling controlled.

## Services and long-term scalability


Services allow your application to evolve without fear.

New requirements usually affect business logic, not routing or storage. When logic is centralized in services, changes are localized. You update behavior without breaking structure.

This is why services are not optional in Charcole.
They are foundational.

## Final thoughts

If repositories protect your data layer,
services protect your business logic.

They give your application a clear voice, a single place where decisions are made, and a structure that remains readable even years later.

Charcole treats services as first-class citizens because sustainable backends are built on clear boundaries — and services are one of the most important ones.
